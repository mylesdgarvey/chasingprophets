# Model Scaffold - Grand Idea

A model scaffold is going to be a visual object in the front end of the system as well as in the back end. It will describe the inputs with extreme precision and the outputs. It also will have a py/js script affiliated with it for local and remote inference/training/other actions. It will be contextualized or non-contextualized. if its contextualized then the variable names will follow a highly specific patterns (for example, the asset datasets that have OHLCV on a day basis ALL have the same column/property/attribute names across different assets. So technically one could form a "OHLCV-specific" model scaffold which will take in ANY OHLCV so long as its column names match the contract. The "contract" is just code that specifies the name of input, its type of values (numerical, text, etc), and its range of values (if its numerical).

## Creating a Scaffold

When a scaffold is created by an admin, they will not only specify the needed input and output contracts, but they'll also paste into text boxes the code that's needed to operate the model and turn it into a model fit (training/inference, any other actions related to this). The system will create the py/js code files in the s3 under the scaffold, and will use the same inference script stored in the scaffold (model fit will store a link to the s3 inference script, scaffold will do the same in the db, but it will also have a link stored for the training script. The admin screen must have a super basic editor that can edit and save the scripts in the s3 for the model scaffold. Furthermore the admin screen for the scaffold must have a local/remote inference option.

## Remote vs Local Inference

Let's get this straight. ALL models will need a remote inference py script. This is because, if the model is fit and then managed under a created prophet (which are entities that apply managed model fits to other data), that prophet will apply the model to new data (model inference). That inference will happen on the server on the scheduler. However. We do want scripts that will handle LOCAL inference. Because once a model fit becomes managed under a prophet, that prophet's minute/daily/weekly etc... predictive performance over the prior 20 days, 40days, 60 days, 120 days, 240 days, 480 days, 1080 days, 1200 days is used as input into the prophet who then sends that as input to the model fit to get out a prediction to compare against the actual (the input of course being strictly in the past). That data is massive to store. So we instead only store the model parameters, run the inference daily to keep track of entity (assets, prophets) predictive performance, compute the aggregate, throw away the inference data but persist the aggregate.

If the user wants to look at the performance, the predictions are computed locally for them using the model fit. So, when a model is fit, its not only the py that will run on lambda on a scheduler. It also will be a js (or corresponding file) that will also run locally upon loading a prophet's or a model fit's page. both of these pages show the inference performance of the prophet/model fit. But to show it, we first need the data. so it uses the LOCAL model inference function to apply to the paired matching and chosen data slice or single observation that is being used as input (the past 30 days, etc...) and uses that to generate the predicted outputs for each day using that fit. So you see, a remote inference for EVERY model scaffold is needed. If the type is chosen as remote, then we assume that inference will always happen remotely, and the react code will instead just query the api to run the inference on the prior 1200 days or so, and have it return back the data set. If the type is chosen as local, the remote is still there of course, but an additional js file will be given to somehow manage the local inference. I need you for the example 2 scaffolds to have them both as local inference.

## Building Model Fits

The ultimate idea for the scaffold approach is that so when admins/users go to build a model fit, they can first choose a preconfigured scaffold (or an asset and then a scaffold), and the system will then return back acceptable datasets and slices that align with that scaffold. So the user can easily just create their own unique model fits by choosing an asset, a data slice or a model scaffold, and then a corresponding set of paired scaffolds or slices whose inputs match the scaffold contract.

## Contextual vs Non-Contextual

The general idea is that if x and y are being used as names, and the type is non-contextual, the code to run training and inference is generic and will be the same regardless of the context. But if the model is context dependent, like for example, the inputs can only be inputs whose names are "close", "close_lag_1", then the code used to operate the model will use those variable names and the data set used with the model scaffold MUST have columns/attributes with those exact names, types, and values that operate within the ranges stated in the scaffold. Otherwise the datasets will not be compatible.
